Orientação testes Sweeping Payments

Teste: Production Funcional Tests For Automatic Sweeping Payments

Visão Geral

O teste de Sweeping Accounts valida a transferência automática de saldos entre contas. O sucesso da execução depende da utilização dos dados bancários da conta principal vinculada ao perfil (PF ou PJ).

Regras de Identificação

O sistema utiliza as chaves principais para a correlação dos dados:

  • Perfil PF: Chave PIX (CPF).
  • Perfil PJ: CNPJ.

Fluxo de Execução

A configuração deste teste é automatizada pelo Gestor de Serviços:

  • Configuração Prévia: Certifique-se de que os dados bancários estão preenchidos e salvos no campo "Configurações de Dados".
  • Seleção do Teste: Selecione o Segmento (PF ou PJ). Ao selecionar "Sweeping Accounts" no Tipo de Teste (Payload), o formulário será alimentado automaticamente com as informações salvas.
  • Validação: Revise se os dados refletidos correspondem à conta vinculada ao CPF/CNPJ antes de iniciar o processo.

⚠️ Atenção QA: A divergência entre a conta configurada e a conta vinculada ao documento (CPF/CNPJ) causará erro imediato na execução. Confirme os dados nas "Configurações de Dados" antes de disparar o teste.

Orientação testes Longa Duração

Testes FVP de Longa Duração (Agendamentos)

Visão Geral

Pertencem à camada FVP e são gerenciados no módulo de Agendamentos. Exigem acompanhamento diário do QA, com regras estritas de saldo em conta para garantir a validação de fluxos que ocorrem ao longo de vários dias.

1. Pix Scheduling 1-2

  • Objetivo: Validação de agendamento de pagamentos.
  • Duração: 2 dias (Encerra no D+2).
  • Requisito de Saldo: Mínimo de R$ 5,00 em conta no início do teste.
Cronograma de Execução (Saldos):
  • D+0: Saldo R$ 2,00
  • D+1: Saldo R$ 2,00
  • D+2: Saldo R$ 1,00

2. Pix Retry 1-3

  • Objetivo: Validação da esteira de retentativa de pagamentos (falha por falta de saldo seguida de sucesso).
  • Duração: 3 dias (Encerra no D+3).
  • Requisito de Saldo: Obrigatoriamente R$ 0,00 (Bloqueio total de pagamentos).
Cronograma de Execução:
  • D+0 a D+2: Saldo R$ 0,00 mantido.
  • D+3 (Finalização): Pagar o valor de R$ 1,00.

Principais Automações

  • Sincronização Automática (Gatilho de Sucesso): O sistema está interligado com a aba de "Gerador de Nomenclatura". Quando um teste de longa duração (ex: Pix Retry 1-3 ou Pix Scheduling 1-2) é registrado com o status "OK", os dados referentes à Marca, Segmento, Tipo de Teste e Data são automaticamente transportados para o formulário de Agendamento.
  • Cálculo Inteligente de Prazos: Ao selecionar o tipo de teste e a data de início, o sistema calcula autonomamente a data de fim da jornada. A lógica define que testes com a palavra "Retry" duram 3 dias (D+3), enquanto o Pix Scheduling dura 2 dias (D+2).
  • Geração de Cronograma Detalhado: Em conjunto com o cálculo de datas, a ferramenta redige automaticamente um bloco de texto com as instruções precisas para cada dia do teste.
  • Integração com Calendário: Existe um botão dedicado para o Google Calendar que, uma vez calculado o prazo, abre a agenda do Google e pré-preenche um evento com o título do teste, as datas de início e fim, e o cronograma detalhado na descrição.
Orientação testes JSR e No Redirect

Testes JSR e No Redirect (API Version 2.2)

1. JSR Pix Verification 1-2

  • Camada: Testes FVP (Módulo de Agendamentos).
  • Duração: 2 dias (Encerra no D+2).
  • Regras de Saldo: Exige saldo mínimo de R$ 2,00 por teste. É obrigatório conferir se o valor foi debitado após a execução e repor o saldo mínimo antes de seguir para os próximos testes da esteira.
  • Configuração Mobile: Prazo de Consentimento Indeterminado, Valor Máximo Diário de R$ 1,00 e Valor Máximo por Transação de R$ 1,00.

2. Production Funcional Tests For No Redirect Automatic Pix Payments

  • Camada: Testes API (Gerador JSON Chicago).
  • Duração: Execução imediata (Geração de Payload).
  • Regras de Saldo e Mobile: Segue a mesma exigência da família JSR (Reposição de saldo de R$ 2,00 e limites do App configurados para R$ 1,00 com prazo Indeterminado).
  • Preenchimento e Automação: CPF é obrigatório para fluxos PF; CNPJ é obrigatório para fluxos PJ.

3. Production Funcional Tests For No Redirect Payments

  • Camada: Testes API (Gerador JSON Chicago).
  • Duração: Execução imediata (Geração de Payload).
  • Regras de Saldo e Mobile: Segue a mesma exigência da família JSR (Reposição de saldo de R$ 2,00 e limites do App configurados para R$ 1,00 com prazo Indeterminado).
  • Preenchimento e Automação: CPF é obrigatório para fluxos PF; CNPJ é obrigatório para fluxos PJ.

4. Production Funcional Tests For no Redirect Automatic Pix Payments Scheduling

  • Camada: Testes API (Gerador JSON Chicago).
  • Duração: Execução imediata (Geração de Payload).
  • Regras de Saldo e Mobile: Segue a mesma exigência da família JSR (Reposição de saldo de R$ 2,00 e limites do App configurados para R$ 1,00 com prazo Indeterminado).
  • Preenchimento e Automação: CPF é obrigatório para fluxos PF; CNPJ é obrigatório para fluxos PJ.

5. Production Funcional Tests For No Redirect Payments Scheduling

  • Camada: Testes API (Gerador JSON Chicago).
  • Duração: Execução imediata (Geração de Payload).
  • Regras de Saldo e Mobile: Segue a mesma exigência da família JSR (Reposição de saldo de R$ 2,00 e limites do App configurados para R$ 1,00 com prazo Indeterminado).
  • Preenchimento e Automação: CPF é obrigatório para fluxos PF; CNPJ é obrigatório para fluxos PJ.
  • Regra de Proxy: O payload gerado possui o campo creditorProxy obrigatoriamente incluído dentro do objeto resource (preenchido com a hash padrão da ferramenta).

🚨 PONTOS CRÍTICOS GERAIS DE EXECUÇÃO (ESTEIRA JSR E NO REDIRECT)

  • Ausência de Prazo "Indeterminado": Interrompa o teste imediatamente se a marca não possuir a opção de tempo "Indeterminado" no aplicativo.
  • Validação Visual Obrigatória: É estritamente obrigatório abrir o dropdown no app e validar a opção configurada. Algumas marcas mascaram "5 anos" como indeterminado, mesmo o campo vindo preenchido corretamente por default.
  • Prevenção de Falsos Negativos: Antes da execução, inspecione no aplicativo bancário se a conta está logada no perfil correto (PF ou PJ). Algumas marcas alternam contas em background, o que causará o fracasso imediato do teste.

Ferramentas

Este menu é dedicado a detalhar o funcionamento e apresentar as interfaces (telas) de cada submódulo do Gestor de Serviços. Estas ferramentas foram projetadas para automatizar tarefas operacionais do QA.

Selecione as opções no menu lateral para visualizar a documentação funcional lado a lado com a tela de cada ferramenta.

1. Nomenclatura (Gerador de Nomenclatura e Evidências)

Gerador de Nomenclatura

Padronização de logs de execução.

OK - Banco do Brasil - PF - Pix Scheduling 1-2 - 25-03-2026 - Android

Nomenclatura de Evidência

Evidencia - Banco do Brasil - PF - Saldo
Evidencia - Banco do Brasil - PF - Versão app
Evidencia - Banco do Brasil - PF - Mensagem de erro
Objetivo:

Garantir a padronização absoluta dos logs de execução e nomes de ficheiros de evidência recolhidos pelos QAs.

Como funciona:
  • O utilizador preenche os parâmetros da execução: Teste Realizado, Sistema Operativo (SO), Data, Marca, Segmento (PF/PJ) e Status (OK, NOK, DCR).
  • O sistema compila estas variáveis num log padronizado (ex: OK - Marca - Segmento - Teste - Data - SO) num campo de texto pronto a copiar.
  • Simultaneamente, gera de forma automática as nomenclaturas corretas para os ficheiros de evidência (Saldo, Versão App, Mensagem de erro).
Inteligência:

Possui um gatilho de sincronização; se o QA marcar um teste de longa duração (como "Pix Scheduling" ou "Pix Retry") com o status "OK", os dados da marca, teste e data são enviados instantaneamente para o módulo de Agendamento.

2. Agendamento (Novo Agendamento)

Novo Agendamento

Planejamento de testes de longa duração.

Objetivo:

Planeamento, monitorização e controlo rigoroso dos testes FVP de longa duração.

Como funciona:
  • O utilizador insere os dados base (Marca, Segmento, Teste) e a Data de Início.
  • O sistema calcula a Data Fim automaticamente com base numa lógica pré-definida: testes "Retry" duram 3 dias (D+3), os restantes duram 2 dias (D+2).
  • É gerado um "Cronograma Detalhado" em ecrã, que descreve as ações diárias necessárias e os saldos obrigatórios para cada dia do teste.
Integrações e Gestão:

Permite guardar o teste numa tabela local (Agendamentos Ativos). Oferece atalhos para exportar a tabela para Excel (.csv) ou criar um ficheiro de backup (.json), bem como restaurar backups anteriores. Inclui um botão para criar o evento diretamente no Google Calendar com o cronograma na descrição.

3. Relatórios (Gerador de Relatórios)

Gerador de Relatórios

Padronização de resultados (NOK / OK).

Texto Raidiam
Objetivo:

Padronizar a comunicação de resultados (erros ou sucessos) para as equipas de desenvolvimento e stakeholders.

Como funciona:
  • O QA seleciona a etapa exata onde o teste falhou (ex: "1. Erro: Antes do Redirecionamento", "3. Erro: Durante Consentimento") ou se foi concluído com sucesso.
  • O formulário adapta-se ao contexto: pede a Versão do App, o Número de Tentativas e a Plataforma.
  • Inclui uma área para a "Análise do QA", com um botão rápido que insere um texto padrão da Raidiam.
  • O sistema compila todas as informações num texto formatado e profissional na área de "Preview", disponibilizando um botão de cópia com um clique.

4. Gerador de JSON (Chicago)

Configuração de Dados

Pessoa Física (PF)

Pessoa Jurídica (PJ)

payload_request.json
Objetivo:

Criação ágil e precisa de massa de dados (payloads JSON) para a execução de testes de API do Open Finance.

Como funciona:
  • Configuração de Dados: O utilizador preenche os dados cadastrais que serão injetados nos payloads. É dividido por perfis: Pessoa Física (Nome, CPF, ISPB, Issuer, Conta) e Pessoa Jurídica (Empresa, CNPJ, ISPB PJ, etc.).
  • Motor de Geração: O QA preenche as chaves de ambiente (Alias, AS-ID), escolhe o Segmento alvo (PF/PJ) e seleciona o Tipo de Teste desejado.
  • Ao clicar em "Gerar JSON", o código processa as regras de negócio: valida documentos (CPF/CNPJ) e constrói o objeto JSON final no ecrã do terminal.
  • Tratamento de Regras: O sistema injeta dinamicamente blocos de código específicos dependendo do teste (como a inclusão obrigatória do CNPJ para testes PJ ou a remoção/inclusão precisa da chave creditorProxy em testes V2.2).
  • Ecossistema: Possui capacidade de guardar e restaurar ficheiros de sessão (.json) para não perder os dados preenchidos, além de integrar o "Modal de Orientações", que dita as regras de negócio de saldo e setup mobile para o QA antes da execução.
